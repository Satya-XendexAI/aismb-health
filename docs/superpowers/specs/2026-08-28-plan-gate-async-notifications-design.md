# Plan-Level Gate & Async WhatsApp Notifications — Design Spec

## Overview

Extends the current single-action confirm gate (`pending_tool` + `AWAITING_CONFIRM`) to support
multi-step action plans generated by an admin-facing LLM agent. When a hospital admin triggers a
delay-management scenario (e.g., "Dr. Sharma is running 38 minutes late"), the LLM reasons over
affected patients, proposes a structured action plan, and waits for admin approval via WhatsApp
before executing. Execution is split into two phases: an atomic DB transaction (Phase 1) and an
async WhatsApp notification sweep (Phase 2).

**Scope:** Admin WhatsApp channel only. No HMS, voice, or calendar integrations in this iteration.

---

## Goals

- Replace ad-hoc single-tool confirm with a typed plan gate that handles N actions atomically
- Guarantee no partial DB state on failure — full rollback if any mutation fails
- Return control to the admin immediately after Phase 1 — notifications fire in the background
- Keep the YES/NO admin flow identical to the existing patient confirm flow

---

## Architecture

```
Admin WhatsApp message
        ↓
handle_message() → AWAITING_CONFIRM check
        ↓
LLM ReAct loop → calls execute_plan({actions: [...]})
        ↓
gate: _build_pending_plan() → session.pending_plan = list[PlanAction]
        ↓
_format_plan_summary() → notifier.send(admin, summary + "Reply YES/NO")
        ↓
session.state = AWAITING_CONFIRM
        ↓
Admin replies YES
        ↓
Phase 1: bulk_reschedule(pending_plan) — single DB transaction
        ↓
Phase 2: notify_patients_bulk(pending_plan) — background thread → job_id
        ↓
notifier.send(admin, "✅ Plan executed. Notifying N patients... (Job: <job_id>)")
```

## Data Model

### New: `PlanAction` dataclass (`models/session.py`)

| Field | Type | Purpose |
|---|---|---|
| `action_type` | `Literal["REASSIGN", "SHIFT", "RETAIN"]` | Determines Phase 1 DB operation |
| `token_id` | `str` | Token being acted on |
| `patient_name` | `str` | Used in admin summary and notification |
| `patient_phone` | `str` | WhatsApp target for Phase 2 |
| `doctor_name` | `str` | Current doctor — used in notification messages |
| `new_doctor_id` | `str \| None` | REASSIGN only |
| `new_doctor_name` | `str \| None` | REASSIGN only — for notification message |
| `new_session_id` | `str \| None` | REASSIGN only |
| `session_id` | `str \| None` | SHIFT only — the doctor_sessions row to update |
| `delay_minutes` | `int \| None` | SHIFT only — added to `doctor_sessions.started_at` |
| `new_token_number` | `int \| None` | Populated by `bulk_reschedule` after REASSIGN insert |
| `notification_message` | `str` | Pre-rendered by LLM; orchestrator patches token number after Phase 1 |

### Modified: `Session` (`models/session.py`)

```python
pending_plan: list[PlanAction] | None = None
```

`pending_tool` and `pending_plan` are mutually exclusive — the gate clears one before setting the
other. `SessionState` is unchanged; `AWAITING_CONFIRM` handles both single and batch flows.

## Gate Flow (`orchestrator/core.py`)

### Plan detection in the main ReAct loop

```
if agent_response.tool_call.tool_name == "execute_plan":
    plan = _build_pending_plan(agent_response.tool_call.args)
    session.pending_plan  = plan
    session.pending_tool  = None
    session.state         = AWAITING_CONFIRM
    summary               = _format_plan_summary(plan, args["summary"])
    notifier.send(admin_phone, summary)
    return
```

### `_format_plan_summary(plan, summary_line) -> str`

Groups actions by type and renders:

```
ACTION PLAN — 14 patients affected by Dr. Sharma delay

• 4 patients → reassigned to Dr. Rao (Cardiology)
• 6 patients → session shifted by 30 minutes
• 4 patients → retained (no change)

Reply *YES* to execute or *NO* to cancel.
```

### AWAITING_CONFIRM branch — plan path

When `session.pending_plan` is set and admin replies YES:

1. Call `bulk_reschedule(session.pending_plan, hospital_id)` — Phase 1
2. If `result.rolled_back`: send admin error message, clear plan, return
3. For each REASSIGN action in `result.succeeded`: patch `notification_message` with actual `new_token_number`
4. Call `notify_patients_bulk(result.succeeded, notifier)` — Phase 2, returns `job_id`
5. Send admin: `"✅ Executed. {len(succeeded)}/{total} DB updates done. Notifying patients... (Job: {job_id})"`
6. Clear `session.pending_plan`, set state to `IDLE`

On NO: clear `pending_plan`, state to `IDLE`, send "Plan cancelled."

## Phase 1: Bulk DB Transaction (`tools/bulk_ops.py`)

### `bulk_reschedule(actions: list[PlanAction], hospital_id: str) -> BulkResult`

All mutations run inside a single `get_connection()` context (existing context manager from
`tools/appointment/database.py`). Any exception triggers a full rollback.

**Per action type:**

| Type | DB operations |
|---|---|
| `REASSIGN` | `cancel_token(conn, token_id)` + `insert_token(conn, new_session_id, ...)` |
| `SHIFT` | `shift_session_start(conn, session_id, delay_minutes)` — one UPDATE per unique session_id |
| `RETAIN` | No-op — recorded as succeeded immediately |

SHIFT is deduplicated: if multiple SHIFT actions share the same `session_id`, the UPDATE runs once
(extracted as a `set` of `(session_id, delay_minutes)` pairs before the loop). `session_id` is
carried directly on `PlanAction` for SHIFT actions — no extra DB lookup required.

### New DB function: `shift_session_start` (`tools/appointment/database.py`)

```sql
UPDATE doctor_sessions
SET started_at = COALESCE(started_at, NOW()) + (delay_minutes || ' minutes')::INTERVAL
WHERE session_id = %s
```

### `BulkResult` dataclass

```python
succeeded:    list[PlanAction]
failed:       list[tuple[PlanAction, str]]   # (action, error_message)
rolled_back:  bool
```

**Failure behaviour:** Any exception inside the transaction aborts and rolls back the entire batch.
`rolled_back=True` is set. The orchestrator surfaces: *"Execution failed — no changes were made.
Please try again."* Retrying requires admin to re-trigger the plan (the SHIFT idempotency risk
means silent auto-retry is prohibited).

## Phase 2: Async WhatsApp Notifications (`workers/notification_worker.py`)

### `notify_patients_bulk(actions, notifier, skip_retain=True) -> str`

- Filters out `RETAIN` actions if `skip_retain=True` (configurable)
- Registers a `JobStatus` entry in an in-process dict keyed by `job_id` (UUID)
- Spawns `threading.Thread(target=_send_loop, ...)`
- Returns `job_id` immediately

### `_send_loop(job_id, actions, notifier)`

Iterates over actions sequentially. For each:
- Calls `notifier.send(action.patient_phone, action.notification_message)`
- On success: increments `job.sent`
- On exception: appends `(patient_phone, error)` to `job.errors`, increments `job.failed`
- Never aborts — continues to next patient regardless of failure
- Sets `job.status = "COMPLETE"` if `failed == 0`, else `"PARTIAL"`

### WhatsApp message templates

| Action | Template |
|---|---|
| `REASSIGN` | "Hi {patient_name}, your appointment has been moved to Dr. {new_doctor_name}. New token: #{token_number}. Apologies for the inconvenience." |
| `SHIFT` | "Hi {patient_name}, Dr. {doctor_name}'s session is running approximately {delay_minutes} minutes late. Your estimated time has been updated." |
| `RETAIN` | "Hi {patient_name}, your appointment with Dr. {doctor_name} is on schedule. No changes needed." |

Messages are pre-rendered into `PlanAction.notification_message` by the LLM when it calls
`execute_plan`, so the worker has no templating logic — it sends the string as-is.

### `get_job_status(job_id: str) -> JobStatus | None`

```python
@dataclass
class JobStatus:
    job_id:  str
    status:  Literal["RUNNING", "COMPLETE", "PARTIAL"]
    total:   int
    sent:    int
    failed:  int
    errors:  list[tuple[str, str]]   # (patient_phone, error_message)
```

## Impact Assessment Tools (LLM reasoning prerequisites)

Before the LLM can generate an `execute_plan` call, it needs to answer four questions. Two new
tools provide this data.

---

### Tool: `get_session_impact`

**File:** `tools/session_impact.py`

**Schema registered in:** `ADMIN_TOOLS`

**Call:** `get_session_impact(doctor_id, date)` — called by the LLM immediately after admin reports
a delay (e.g., "Dr. Sharma is running 1 hour late").

**What it returns:**

```json
{
  "session_id": "...",
  "doctor_name": "Dr. Sharma",
  "department": "Cardiology",
  "total_waiting": 14,
  "patients": [
    {
      "token_id": "...",
      "token_number": 3,
      "patient_name": "Ravi Kumar",
      "patient_phone": "91...",
      "age": 72,
      "is_elderly": true,
      "location": "Nellore",
      "distance_km": 170,
      "distance_confidence": "high",
      "is_outstation": true
    }
  ]
}
```

**DB query:** Single JOIN across `tokens → patients → doctor_sessions` filtered by `doctor_id`,
`date`, and `status = 'WAITING'`. Reuses `get_connection()` from `tools/appointment/database.py`.

**Elderly threshold:** `age >= 60` → `is_elderly: true`.

**Distance:** Each patient's `location` is passed through `_resolve_distance()` (see below) against
the hospital's city. Result is merged into the patient row before returning.

---

### Utility: `_resolve_distance` (inside `tools/session_impact.py`)

Calls `gemini-3.5-flash-lite` (same model as `_parse_query` in `kg_retriever.py`) with a
structured JSON prompt:

**Prompt:**
```
Given:
  Hospital location: {hospital_city}
  Patient location: {patient_location}

Return JSON:
  estimated_km: integer (straight-line road distance estimate)
  confidence: "high" | "medium" | "low"
  classification: "local" | "outstation"

Rules:
- "outstation" if patient is from a different city or district
- "local" if within the same city/metro area
- confidence "low" if location string is vague (neighbourhood, landmark, etc.)
```

**Fallback:** If `confidence == "low"` or LLM call fails, fall back to simple string comparison:
`is_outstation = patient_location.lower() != hospital_city.lower()`, `estimated_km = None`.

**Result used as:** `is_outstation` flag is the primary signal for admin summary. `estimated_km`
is surfaced as context only when `confidence` is `"high"` or `"medium"`.

---

### Tool: `find_available_doctors`

**File:** `tools/session_impact.py` (same file, separate function)

**Schema registered in:** `ADMIN_TOOLS`

**Call:** `find_available_doctors(specialization, date)` — called by the LLM to find alternative
doctors who could absorb reassigned patients.

**Challenge:** Specialization lives in Neo4j; session availability lives in PostgreSQL. This tool
bridges both in two steps:

**Step 1 — Neo4j:** Reuse `find_doctors_by_specialization(spec)` from `kg_retriever.py` to get
all `doctor_id`s matching the specialization.

**Step 2 — PostgreSQL:** Query `doctor_sessions` for those `doctor_id`s on the given date with
`status = 'OPEN'`, joining `tokens` for queue depth and `doctors` for consultation time.

**Note on availability window:** `doctor_sessions` has no stored end time. The window is derived:
`estimated_session_end = started_at (or avg_checkin_time) + (current_queue × avg_consultation_minutes)`.
No schema change needed — both inputs are already in the DB.

```sql
SELECT d.doctor_id, d.name, ds.session_id, ds.started_at,
       d.avg_checkin_time, d.avg_consultation_minutes,
       COUNT(t.token_id) AS current_queue,
       COALESCE(ds.started_at, NOW()::date + d.avg_checkin_time)
         + (COUNT(t.token_id) * d.avg_consultation_minutes * INTERVAL '1 minute')
         AS estimated_session_end
FROM doctors d
JOIN doctor_sessions ds ON d.doctor_id = ds.doctor_id
LEFT JOIN tokens t ON t.session_id = ds.session_id AND t.status = 'WAITING'
WHERE d.doctor_id = ANY(%s)
  AND ds.date = %s
  AND ds.status = 'OPEN'
  AND d.hospital_id = %s
GROUP BY d.doctor_id, d.name, ds.session_id, ds.started_at,
         d.avg_checkin_time, d.avg_consultation_minutes
ORDER BY current_queue ASC
```

**Returns:**

```json
{
  "specialization": "Cardiology",
  "available_doctors": [
    {
      "doctor_id": "dr-rao--chn",
      "doctor_name": "Dr. Rao",
      "session_id": "...",
      "current_queue": 4,
      "started_at": "09:00:00",
      "estimated_session_end": "12:40:00"
    }
  ]
}
```

The LLM uses both `current_queue` and `estimated_session_end` to decide how many patients each
doctor can realistically absorb — e.g., "Dr. Rao finishes at 12:40, Dr. Mehta at 13:15 — Rao
has more room for reassignments."

### Updated LLM Reasoning Flow

With these two tools, the full admin flow becomes:

```
Admin: "Dr. Sharma will be 1 hour late"
        ↓
LLM calls get_session_impact(doctor_id="dr-sharma--chn", date="2026-08-28")
→ 14 patients, 3 elderly, 2 outstation
        ↓
LLM calls find_available_doctors(specialization="Cardiology", date="2026-08-28")
→ Dr. Rao (4 in queue), Dr. Mehta (7 in queue)
        ↓
LLM reasons: elderly + outstation → reassign to Dr. Rao (lower queue)
             others → shift by 60 mins or retain
        ↓
LLM calls execute_plan({actions: [...]})
        ↓
Gate → admin confirms → Phase 1 + Phase 2
```

## Constraints

- `pending_tool` and `pending_plan` are mutually exclusive — always clear one before setting the other
- SHIFT UPDATE must not be auto-retried silently — `started_at` shifts are additive
- `notify_patients_bulk` never aborts mid-loop — PARTIAL is surfaced to admin, not silently swallowed
- Worker uses in-process dict for MVP; interface is stable enough to swap to Redis/Celery later without touching the orchestrator
